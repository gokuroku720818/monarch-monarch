# Monarch Monarch Original-Parity Restoration Design

**Date:** 2026-09-28  
**Baseline:** V183  
**Primary goal:** Reconstruct the HTML edition so that behavior is driven by evidence from the original Windows game, not by guessed improvements, and make remaining uncertainty explicit and testable.

## 1. Purpose

The project is no longer a sequence of isolated “looks closer to the original” patches. From V184 onward it becomes an evidence-backed original-parity program.

Success means:

- Original MAP, title, commander-marker, WAV, and MIDI source data remain byte-faithful where already recovered.
- Gameplay rules are implemented only when supported by original evidence.
- Each restored rule has a provenance record.
- Every changed behavior has a failing-first regression test.
- Browser behavior is checked through the actual playable UI, not only isolated helper functions.
- Unknown or partially verified behavior stays explicitly marked as unknown or partial.
- The project never claims whole-game 1:1 parity unless dynamic original-versus-browser comparison supports that claim.

## 2. Authoritative evidence hierarchy

Every parity rule must link to one or more of the following sources.

1. **Original executable evidence**
   - Static disassembly of the user-provided `lm_win.exe`.
   - Exact function/address ranges must be recorded where known.
   - A static reading proves only what the instructions and data flow establish; it does not prove every runtime consequence.

2. **Original data-file evidence**
   - `Data*.lib`, `Data*.dat`, MAP records, original WAV files, original MIDI files, and other data contained in the user-provided original archive.
   - Decoding logic must be reproducible from checked-in scripts/tests where practical.

3. **Original runtime evidence**
   - Direct observation of the original Windows executable under a compatible runtime or captured original gameplay.
   - When available, this outranks assumptions inferred only from the browser build.

4. **Primary external documentation**
   - Contemporary publisher/developer documentation, manuals, screenshots, or official product pages.
   - Use for controls, presentation, supported platform/audio details, and other externally documented behavior.

5. **Current restoration behavior**
   - Existing V183 behavior is never evidence for the original by itself.
   - It may be retained only when it has existing original evidence or when it is explicitly marked as a browser adaptation.

## 3. Evidence status model

Each rule tracked by the parity system must be assigned exactly one status:

- **CONFIRMED** — Original evidence establishes the rule sufficiently to implement and regression-test it.
- **PARTIAL** — Some parts are established, but at least one timing, random, state, visual, or edge-condition detail is not.
- **UNKNOWN** — No adequate evidence yet.
- **BROWSER_ADAPTATION** — Deliberate browser-only behavior that is not claimed to be original.

A rule may move toward stronger evidence only when a source is added. “It feels right” cannot change status.

## 4. Parity domains

The evidence inventory and regression suite will organize behavior into these domains:

1. Stage/data loading
2. Unit creation and slot lifecycle
3. Mouse input, selection, and command-mode flow
4. Unit movement and path selection
5. Action adjacency and height rules
6. Bridge/fence/base/terrain construction and destruction
7. Combat, damage, merging, surrender, and death
8. Production, economy, resource costs, territory, and maintenance
9. Commander/castle behavior
10. Neutral-unit AI
11. CPU faction AI
12. Random-number-dependent decisions
13. Simulation timing and action scheduling
14. Win/loss/stage-completion flow
15. Score/result screens
16. Rendering and original UI presentation
17. WAV effects and event mapping
18. MIDI selection, transitions, and playback adaptation

## 5. Architecture

### 5.1 Preserve V183 as the immutable behavioral baseline

V183 remains archived. V184 and later versions are generated by exact-blob-gated upgrade scripts, following the existing release pattern.

Changes must not rewrite unrelated embedded assets or silently alter already verified rules.

### 5.2 Original evidence manifest

Create a machine-readable parity manifest under `parity/`.

The manifest records, for each rule:

- stable rule ID
- domain
- short description
- evidence status
- original source type
- original EXE address/range where applicable
- original data-file reference where applicable
- HTML implementation function(s)
- test file(s)
- known limitations
- first restored version

This manifest becomes the canonical map between reverse-engineering evidence and shipped browser behavior.

### 5.3 Extracted-code audit

Add tooling that extracts relevant JavaScript functions from the shipped HTML and audits them against the parity manifest.

The first version does not restructure the monolithic HTML engine. It treats the shipped HTML as the product and builds verification around it, avoiding a high-risk rewrite.

### 5.4 Scenario-driven regression harness

Add deterministic scenario tests that construct the minimum map/unit/resource state needed to exercise a confirmed original rule.

A scenario test must:

- execute functions extracted from the shipped HTML, not a hand-copied reimplementation;
- establish the pre-state explicitly;
- assert the relevant post-state;
- verify rejection paths preserve previous commands/state when the original rule rejects an action;
- cover boundary values when original comparisons use strict or inclusive limits.

Where random behavior is involved, random inputs must be injectable or otherwise controlled for the test.

### 5.5 Browser end-to-end verification

For behaviors reachable through the UI, add/retain browser checks that verify the actual sequence:

selection → command UI → target choice → simulation work → resulting state.

Browser checks must capture:

- page/console errors;
- selection/command state;
- relevant unit/tile/resource state before and after;
- whether command pause/resume behavior is preserved.

### 5.6 Long-run map invariants

The existing 75-map smoke testing evolves into invariant testing.

At minimum, long-run checks should detect:

- invalid/dead unit selections;
- recycled-slot stale command state;
- invalid tile/unit coordinates;
- impossible resource values;
- simulation stalls caused by impossible work targets;
- stage-data mutation outside expected gameplay;
- uncaught JavaScript errors.

These invariants do not by themselves prove parity. They prove restoration stability.

## 6. Original-mode versus browser adaptations

The project must distinguish original behavior from convenience features.

The final user-facing design will support an **Original mode** in which:

- control semantics follow confirmed original mouse behavior;
- browser-only shortcuts that alter original interaction semantics are disabled or hidden;
- original data, gameplay rules, timing rules, and UI behavior are preferred wherever confirmed.

Optional convenience behaviors such as touch adapters, mobile compatibility, or extra shortcuts may remain only as clearly separated browser adaptations if they do not contaminate original-mode rule execution.

V184 does not yet remove all adaptations. It establishes the classification and testing framework first.

## 7. V184 first parity correction

### 7.1 Confirmed defect

Original map M_032 contains two destructible fence cores at the same x/y column but different heights, including a low and high fence.

V183 destruction handling can re-search the whole x/y column during an active fence-destruction command. That permits a command issued against one height to switch to another fence in the same column after the original target disappears.

The original action path uses the stored target cell coordinates, including z, rather than retargeting an unrelated height in the same x/y column.

### 7.2 V184 behavior

- Normalize a clicked fence upper-half tile to its matching core once when issuing the command.
- Store that exact core x/y/z as the destruction target.
- During execution, inspect only the stored target cell.
- Once that structure is gone or no longer destructible, end the destruction command.
- Never reselect another fence merely because it shares x/y.
- Preserve existing action-height, route, command-pause, cost, damage, and destruction rules.

### 7.3 V184 regression

Create a failing-first test derived from the real M_032 stacked-fence geometry.

The test must prove:

- V183 switches or remains stuck because the x/y column search finds the other-height fence;
- V184 destroys/finishes the selected target without retargeting the other height;
- the untouched fence remains unchanged;
- prior fence/bridge/work-height regressions still pass.

## 8. Release gates from V184 onward

A parity release may be published only when all applicable gates succeed:

1. Exact baseline blob accepted by the upgrader.
2. New failing-first regression demonstrated against the prior version.
3. New regression passes against both LITE and FULL builds when both builds contain the affected engine.
4. Previous gameplay regressions pass.
5. Original 75-map/title/commander-marker/WAV parity checks pass.
6. Embedded asset payloads unrelated to the patch remain unchanged.
7. JavaScript syntax checks pass.
8. Browser scenario check passes for UI-reachable behavior.
9. 75-stage stability/invariant run passes at the configured duration.
10. GitHub Actions succeeds before publishing `index.html`.
11. GitHub Pages deployment succeeds.
12. Release report states what is confirmed, partial, unknown, and browser-adapted.

## 9. Parallel investigation strategy

After V184 establishes the harness, independent evidence domains may be investigated in parallel:

- movement/pathfinding;
- construction/destruction;
- combat;
- economy/production;
- neutral AI;
- CPU AI;
- timing/random;
- UI/audio/results.

Parallel investigators may produce evidence notes and proposed tests, but they must not independently edit the same shipped HTML. Production integration remains serialized through exact-blob-gated releases.

## 10. Non-goals

This effort does not:

- rewrite the game in a new framework merely for code cleanliness;
- invent balance changes or quality-of-life gameplay changes inside Original mode;
- treat modern browser behavior as original evidence;
- replace original art/audio with approximations when original assets are already available;
- claim Windows MIDI timbre equivalence when browser playback uses a rendered/synthesized adaptation;
- claim full dynamic equivalence from static EXE analysis alone.

## 11. Completion criteria for “original-identical”

The label “original-identical” may be used only if all of the following are true:

- all gameplay-critical parity-manifest rules are CONFIRMED;
- all 75 original stages load from verified original data;
- core commands, movement, construction, combat, economy, AI, victory/defeat, and scoring have deterministic regression coverage;
- long-run invariants pass across all stages;
- relevant browser E2E flows pass;
- original asset parity checks pass;
- remaining BROWSER_ADAPTATION behavior is isolated from Original mode;
- any behavior that cannot be dynamically compared to the original executable is explicitly excluded from the claim.

Until then, releases remain labeled as restoration builds with documented parity coverage and limitations.

## 12. V184 deliverables

V184 is the first release under this architecture and must include:

- `parity/original-parity.json` (initial evidence manifest);
- `tools/audit_parity.py` (manifest/source/test audit);
- `tests/test_fence_exact_target_height.js` (M_032 stacked-fence regression);
- `scripts/upgrade_v184.py` (exact V183 blob-gated patch);
- updated GitHub Actions gates;
- `V184_ORIGINAL_COMPARISON_REPORT.md`;
- V184 LITE and FULL packaged outputs;
- successful GitHub Pages deployment.
